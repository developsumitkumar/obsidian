# SQL Data Modelling — Basic to Advanced 

# SECTION 1: What is it? 

Imagine you are asked to **design a new library from scratch** — not just organize books, but decide: *Where will the shelves go? How will books be grouped? Where do we note down who borrowed what? How do we avoid confusion if two books have the same name?*

**Before you buy a single shelf, you first draw a PLAN on paper** — which sections exist, what information each section holds, and how sections relate to each other (e.g., "Student" section connects to "Issued Books" section).

**That planning exercise — deciding what data you need to store, how to organize it into logical groups, and how those groups relate to each other — is called Data Modelling.**

In simple words:

> Data Modelling is the **blueprint** of a database. It's not about writing SQL queries yet — it's about deciding *what boxes (tables) you need, what goes inside each box (columns), and how the boxes are connected (relationships)* — BEFORE you build anything.

---

# SECTION 2: Why do we need it?

## The Business Problem

Imagine a company starts building its database **without any plan** — just adding tables and columns randomly whenever a new requirement comes up.

**What goes wrong without Data Modelling:**

* **Data Duplication:** A customer's address gets typed into 10 different tables. When the customer moves houses, you now have to update it in 10 places — miss one, and your data is inconsistent forever.
* **Confusing Relationships:** Nobody knows if one Customer can have multiple Orders, or if an Order can belong to multiple Customers — leading to wrong reports.
* **Poor Performance:** Badly designed tables force the database to do unnecessary heavy lifting (huge unindexed scans, unnecessary JOINs) for even simple questions.
* **Scaling Nightmares:** As the business grows (more products, more regions, more transaction types), a poorly modeled database becomes almost impossible to extend without breaking existing features.
* **Wrong Business Decisions:** If "Total Sales" can be calculated 3 different (inconsistent) ways because of a messy structure, different teams report different numbers to management.

**Data Modelling prevents all of this by forcing you to think through the structure BEFORE writing a single `CREATE TABLE` statement.**

# SECTION 3: Real-World Analogy

### Hospital Analogy

Before building a hospital's records system, you must decide: Is "Patient" a separate concept from "Appointment"? Can one Patient have many Appointments with many different Doctors? This decision (One Patient → Many Appointments) IS data modelling — deciding the **shape of relationships** before construction.

### Bank Analogy

A bank must decide: Can one Customer own multiple Accounts (Savings + Current)? Can one Account be jointly owned by multiple Customers? These "can one X have many Y" questions define your **cardinality** (a technical word we'll explain in Section 4) — and this is decided at the modelling stage, not while writing queries.

### Amazon Analogy

Amazon must model: One Customer → Many Orders. One Order → Many Products (via OrderDetails, since one order can contain multiple items and one product can appear in multiple orders). This many-to-many relationship between Orders and Products needs a special modelling technique (a "bridge/junction table") — which we'll cover in Section 6.

We'll keep using **Hospital, Bank, and Amazon** as our running examples throughout this guide.

# SECTION 4: Technical Definition

**Data Modelling** is the process of defining the structure, relationships, and constraints of data before implementing it in a database — typically progressing through three levels of detail.

**Key terms explained (in order of complexity):**

|Term|Simple Meaning|
|-|-|
|**Entity**|A "thing" you want to store data about — like Customer, Product, Order. Becomes a **Table**.|
|**Attribute**|A property/detail of an entity — like Customer's Name, Email. Becomes a **Column**.|
|**Primary Key (PK)**|A column that uniquely identifies each row (like an Aadhar number — never repeats).|
|**Foreign Key (FK)**|A column in one table that points to the Primary Key of another table, creating a link/relationship.|
|**Relationship**|How two entities are connected — e.g., a Customer "places" Orders.|
|**Cardinality**|The "how many" rule of a relationship: One-to-One, One-to-Many, or Many-to-Many.|
|**Normalization**|The process of organizing tables to remove duplicate/redundant data.|
|**Denormalization**|The opposite — intentionally combining tables to make reading data faster (used in reporting systems).|
|**ER Diagram (Entity-Relationship Diagram)**|A visual drawing showing entities, their attributes, and how they connect.|
|**Schema**|The overall named structure — the full set of tables, columns, and relationships in a database.|

**Three Levels of Data Modelling:**

|Level|What it focuses on|Example|
|-|-|-|
|**Conceptual Model**|High-level business entities only, no technical detail|"Customer places Order"|
|**Logical Model**|Adds attributes, keys, and relationships (still no database-specific detail)|Customer(CustomerID, Name, Email) → Order(OrderID, CustomerID, Date)|
|**Physical Model**|Adds actual database-specific details — data types, indexes, constraints|`CustomerID INT PRIMARY KEY, Name VARCHAR(100)`|

# SECTION 5: Architecture (Visual — How a Data Model is Built)

```
   BUSINESS REQUIREMENT
   "We need to track customers and their orders"
            |
            v
  +----------------------+
  |  CONCEPTUAL MODEL     |    <- Just boxes and relationship names
  |  [Customer] --places--> [Order]
  +----------------------+
            |
            v
  +----------------------------------------------+
  |  LOGICAL MODEL                                 |    <- Add attributes + keys (no data types yet)
  |  Customer(CustomerID*, Name, Email)            |
  |  Order(OrderID*, CustomerID(FK), OrderDate)    |
  +----------------------------------------------+
            |
            v
  +--------------------------------------------------------------+
  |  PHYSICAL MODEL                                                 |   <- Real SQL, ready to build
  |  CREATE TABLE Customer (CustomerID INT PRIMARY KEY, Name       |
  |  VARCHAR(100), Email VARCHAR(150));                             |
  |  CREATE TABLE Orders (OrderID INT PRIMARY KEY, CustomerID INT   |
  |  FOREIGN KEY REFERENCES Customer(CustomerID), OrderDate DATE);  |
  +--------------------------------------------------------------+
            |
            v
      ACTUAL DATABASE (Azure SQL / MySQL / PostgreSQL etc.)
```

**Component explanation:**

* **Conceptual Model** — the "napkin sketch" stage. Business stakeholders (who don't know SQL) can understand this.
* **Logical Model** — the "engineering blueprint" stage. Data engineers and architects design this; still technology-independent.
* **Physical Model** — the "construction" stage. This is technology-specific (SQL Server vs MySQL might differ slightly in data types).
* **Actual Database** — the final built structure sitting on a real server, ready to store real data.

# SECTION 6: Step-by-Step — What Happens Internally (The Modelling Process)

1. **Step 1 — Gather Requirements:** Talk to business stakeholders. E.g., "We run a hospital and need to track Patients, Doctors, and Appointments."
2. **Step 2 — Identify Entities:** List out the "nouns" that matter — Patient, Doctor, Appointment, Department.
3. **Step 3 — Identify Attributes:** For each entity, list its details — Patient(Name, DOB, Phone), Doctor(Name, Specialization).
4. **Step 4 — Identify Relationships & Cardinality:** Decide how entities connect — "One Doctor can have Many Appointments" (One-to-Many), "One Appointment involves exactly One Patient and One Doctor."
5. **Step 5 — Assign Primary Keys:** Every entity gets a unique identifier — PatientID, DoctorID, AppointmentID.
6. **Step 6 — Add Foreign Keys to Represent Relationships:** Appointment table gets PatientID and DoctorID columns as Foreign Keys, linking back to the Patient and Doctor tables.
7. **Step 7 — Apply Normalization Rules:** Check for repeated/duplicate data and split tables further if needed (explained in detail in Section 9 equivalent — see Normalization deep-dive below).
8. **Step 8 — Draw the ER Diagram:** Visually represent all entities, attributes, and relationships for team review.
9. **Step 9 — Convert to Physical Model:** Translate the logical model into actual `CREATE TABLE` statements with real data types and constraints.
10. **Step 10 — Review & Validate:** Cross-check the model against real business questions — "Can I find all appointments for a doctor next week?" If yes, model likely works. If painful, re-model.

# SECTION 8: Project Example

### Project: Hospital Appointment Management System

**Business Requirement:**
Design a database where Patients can book Appointments with Doctors. Each Doctor belongs to a Department. The system must avoid duplicate patient/doctor data and support fast lookup of "all appointments for a doctor this week."

**Architecture (Entities identified):**

```
Department  ---- has many ---->  Doctor
Doctor      ---- has many ---->  Appointment
Patient     ---- has many ---->  Appointment
```

**Data Flow (Modelling Decisions):**

1. `Department(DepartmentID*, DepartmentName)`
2. `Doctor(DoctorID*, Name, DepartmentID [FK])`
3. `Patient(PatientID*, Name, DOB, Phone)`
4. `Appointment(AppointmentID*, PatientID [FK], DoctorID [FK], AppointmentDate, Status)`

**Challenges:**

* Should "Symptoms" be stored in the Appointment table, or a separate table (since one appointment could have multiple symptoms)? → Decided: separate `AppointmentSymptoms` table (one-to-many) to avoid cramming multiple values into one column (this violates a normalization rule — see Section on Normalization).
* Should Doctor's Department be a text column or a Foreign Key? → Decided: Foreign Key, so department names stay consistent and can be renamed in one place.

**Solution:**
A normalized structure of 5 tables (Department, Doctor, Patient, Appointment, AppointmentSymptoms) connected via Foreign Keys, with no duplicated text data anywhere.

**Output:**
Any report — "Show me Dr. Mehta's appointments for the department of Cardiology this week" — can be answered with a clean JOIN across just 3 tables, fast and accurate.

# SECTION 9: Code Examples

## Beginner Level — Basic Table Creation from a Simple Model

```sql
CREATE TABLE Customer (
    CustomerID INT PRIMARY KEY,
    Name VARCHAR(100),
    Email VARCHAR(150)
);

CREATE TABLE Orders (
    OrderID INT PRIMARY KEY,
    CustomerID INT,
    OrderDate DATE,
    FOREIGN KEY (CustomerID) REFERENCES Customer(CustomerID)
);
```

**Line-by-line explanation:**

* `CustomerID INT PRIMARY KEY` → this column will uniquely identify each customer; no two customers can share this value.
* `FOREIGN KEY (CustomerID) REFERENCES Customer(CustomerID)` → this tells SQL: "the CustomerID in Orders MUST already exist in the Customer table" — this is how the **relationship** from the model becomes enforced in real data.

## Medium Level — Modelling a Many-to-Many Relationship (Amazon-style)

```sql
CREATE TABLE Product (
    ProductID INT PRIMARY KEY,
    ProductName VARCHAR(150),
    Price DECIMAL(10,2)
);

CREATE TABLE Orders (
    OrderID INT PRIMARY KEY,
    CustomerID INT,
    OrderDate DATE
);

-- Bridge / Junction Table for Many-to-Many relationship
CREATE TABLE OrderItems (
    OrderID INT,
    ProductID INT,
    Quantity INT,
    PRIMARY KEY (OrderID, ProductID),
    FOREIGN KEY (OrderID) REFERENCES Orders(OrderID),
    FOREIGN KEY (ProductID) REFERENCES Product(ProductID)
);
```

**Explanation:** One Order can contain many Products, and one Product can appear in many Orders — this is a **Many-to-Many relationship**. A single table can't represent this directly, so we create a **bridge table** (`OrderItems`) sitting in the middle, holding a Foreign Key to BOTH sides plus its own extra detail (`Quantity`). Its Primary Key is a **composite key** (two columns combined) — explained fully in Section 15.

## Advanced Level — Star Schema for Reporting/Data Warehouse

```sql
-- Dimension Tables (descriptive, "who/what/when/where")
CREATE TABLE DimCustomer (
    CustomerKey INT PRIMARY KEY,
    CustomerName VARCHAR(100),
    City VARCHAR(100)
);

CREATE TABLE DimProduct (
    ProductKey INT PRIMARY KEY,
    ProductName VARCHAR(150),
    Category VARCHAR(100)
);

CREATE TABLE DimDate (
    DateKey INT PRIMARY KEY,
    FullDate DATE,
    Month VARCHAR(20),
    Year INT
);

-- Fact Table (numeric, "what happened")
CREATE TABLE FactSales (
    SalesID INT PRIMARY KEY,
    CustomerKey INT FOREIGN KEY REFERENCES DimCustomer(CustomerKey),
    ProductKey INT FOREIGN KEY REFERENCES DimProduct(ProductKey),
    DateKey INT FOREIGN KEY REFERENCES DimDate(DateKey),
    QuantitySold INT,
    TotalAmount DECIMAL(10,2)
);
```

**Explanation:** This is a **Star Schema**, used in Data Warehouses (reporting systems, NOT day-to-day transaction systems). A central **Fact table** (`FactSales`, holding numbers/measurements) connects to multiple surrounding **Dimension tables** (`DimCustomer`, `DimProduct`, `DimDate`, holding descriptive context). This design is intentionally *less normalized* than a transactional system because it's optimized for **fast reading/reporting**, not for avoiding every last bit of duplication. Fully explained in Section 18.

# SECTION 10: Interview Questions

## 10 Easy

1. **What is Data Modelling?**
*Answer:* The process of designing how data will be structured, stored, and related in a database before building it. *Why asked:* Foundational understanding check.
2. **What is an Entity?**
*Answer:* A real-world object or concept we want to store data about (e.g., Customer, Product) — becomes a table. *Why asked:* Basic terminology.
3. **What is an Attribute?**
*Answer:* A property/detail of an entity (e.g., Customer's Name) — becomes a column. *Why asked:* Basic terminology.
4. **What is a Primary Key?**
*Answer:* A column that uniquely identifies every row in a table, and cannot be NULL or duplicated. *Why asked:* Core building block of any model.
5. **What is a Foreign Key?**
*Answer:* A column that references another table's Primary Key, creating a relationship between two tables. *Why asked:* Core building block of relationships.
6. **What is an ER Diagram?**
*Answer:* A visual diagram showing entities, their attributes, and the relationships between them. *Why asked:* Communication tool question.
7. **What is Normalization (in one line)?**
*Answer:* The process of organizing data to reduce duplication and improve consistency. *Why asked:* Very frequently asked basic concept.
8. **What is a Composite Key?**
*Answer:* A Primary Key made up of two or more columns combined together. *Why asked:* Tests understanding beyond single-column keys.
9. **What is Cardinality in a relationship?**
*Answer:* It describes the "how many" — One-to-One, One-to-Many, or Many-to-Many between two entities. *Why asked:* Basic relationship-design concept.
10. **What is the difference between a Logical Model and a Physical Model?**
*Answer:* Logical model defines entities/attributes/relationships without technology detail; Physical model adds actual data types, constraints, and is technology-specific. *Why asked:* Tests understanding of the modelling process stages.

## 10 Medium

1. **What is 1NF, 2NF, and 3NF?**
*Answer:* These are Normal Forms — progressive rules to reduce redundancy. 1NF: no repeating groups/each cell holds one value. 2NF: 1NF + no partial dependency on part of a composite key. 3NF: 2NF + no transitive dependency (non-key columns shouldn't depend on other non-key columns). *Why asked:* Extremely common — tests real normalization understanding, not just definitions.
2. **How do you model a Many-to-Many relationship?**
*Answer:* Using a bridge/junction table that holds Foreign Keys from both related tables, often forming a composite Primary Key. *Why asked:* Real-world scenario every engineer faces (Orders-Products, Students-Courses).
3. **What is Denormalization and when would you use it?**
*Answer:* Intentionally combining normalized tables to reduce JOINs and speed up read-heavy reporting systems — used in Data Warehouses/BI dashboards. *Why asked:* Tests awareness that normalization isn't always the goal.
4. **What is a Surrogate Key vs a Natural Key?**
*Answer:* A Surrogate Key is an artificial, system-generated ID (like an auto-incrementing number) with no business meaning; a Natural Key is a real-world unique attribute (like Aadhar number, Email). Surrogate keys are preferred because natural keys can change or aren't always unique. *Why asked:* Practical design decision question.
5. **What is a One-to-One relationship, and when is it used?**
*Answer:* Each row in Table A matches exactly one row in Table B — used to split a table for security/performance reasons (e.g., Employee basic info vs Employee sensitive salary info in a separate restricted table). *Why asked:* Tests knowledge of a less common but real modelling pattern.
6. **What is Referential Integrity?**
*Answer:* A rule ensuring a Foreign Key value must always match an existing Primary Key value in the referenced table (no "orphan" records pointing to nothing). *Why asked:* Core data-quality concept.
7. **What is the difference between OLTP and OLAP data models?**
*Answer:* OLTP (Online Transaction Processing) models are highly normalized for fast, accurate day-to-day transactions (e.g., banking app). OLAP (Online Analytical Processing) models are often denormalized (Star Schema) for fast complex reporting/analytics. *Why asked:* Critical for data engineering roles specifically.
8. **What is a Junction/Bridge Table?**
*Answer:* A table created solely to resolve a Many-to-Many relationship, holding Foreign Keys to both related tables. *Why asked:* Same core concept as many-to-many, phrased differently — very common.
9. **Why do we avoid storing multiple values in a single column (e.g., "Cardiology, Neurology" in one cell)?**
*Answer:* It violates First Normal Form (1NF), making the data hard to search, filter, and JOIN accurately — you'd need to split it into a separate related table instead. *Why asked:* Practical normalization scenario.
10. **What is a Slowly Changing Dimension (SCD)?**
*Answer:* A technique in Data Warehousing to handle changes in dimension data over time (e.g., a customer changes city) — Type 1 overwrites old data, Type 2 keeps full history with new rows. *Why asked:* Common Data Engineering interview topic bridging modelling with real pipelines.

## 10 Advanced

1. **Explain the difference between Star Schema and Snowflake Schema.**
*Answer:* Star Schema keeps Dimension tables flat/denormalized (fewer JOINs, faster reads). Snowflake Schema further normalizes Dimension tables into sub-dimensions (e.g., DimProduct splits into DimProduct + DimCategory), saving storage but requiring more JOINs. *Why asked:* Senior-level Data Warehouse design knowledge.
2. **When would you deliberately denormalize a model, and what are the trade-offs?**
*Answer:* Denormalize for read-heavy reporting/analytics systems to reduce JOIN overhead; trade-off is increased storage and higher risk of data inconsistency during updates, so it's usually done in read-only/batch-refreshed systems, not live transactional ones. *Why asked:* Tests real design judgment, not memorized rules.
3. **How would you model a system where a Product's price changes over time, but historical orders must still reflect the price at the time of purchase?**
*Answer:* Store the price directly on the OrderItems/Fact table at the time of the transaction (a snapshot), rather than only relying on the live Product table — this is a form of handling Slowly Changing Dimensions / historical accuracy. *Why asked:* Classic real-world data integrity trap.
4. **Explain Boyce-Codd Normal Form (BCNF) and how it differs from 3NF.**
*Answer:* BCNF is a stricter version of 3NF — it requires that for every functional dependency, the left-hand side must be a super key, resolving rare edge cases that 3NF doesn't fully cover (like when a table has multiple overlapping candidate keys). *Why asked:* Tests deep theoretical grounding.
5. **How do you model hierarchical data (e.g., an organization's reporting structure) in a relational model?**
*Answer:* Using a self-referencing Foreign Key (e.g., Employee table with a ManagerID column pointing back to EmployeeID in the same table), or for deep hierarchies, using techniques like Adjacency List, Path Enumeration, or Nested Sets. *Why asked:* Tests advanced structural design skill.
6. **What is a Fact Table's grain, and why does it matter?**
*Answer:* "Grain" defines the level of detail one row in the Fact table represents (e.g., one row per order line item vs one row per order) — getting the grain wrong leads to double-counting or loss of detail in every downstream report. *Why asked:* Core Data Warehousing design principle, frequently misunderstood.
7. **How would you design a data model to support both OLTP and near-real-time analytics without duplicating too much infrastructure?**
*Answer:* Keep OLTP normalized for transactions, then use CDC (Change Data Capture) or ETL/ELT pipelines to continuously flow data into a separate denormalized OLAP/Star Schema model for analytics — avoiding running heavy analytical queries directly on the transactional system. *Why asked:* Tests real architecture-level thinking for a Data Engineer role.
8. **What are Degenerate Dimensions in a Star Schema?**
*Answer:* Dimension-like values (e.g., Invoice Number, Order Number) stored directly in the Fact table without a separate dimension table, because they have no additional descriptive attributes worth modelling separately. *Why asked:* Advanced Data Warehousing vocabulary check.
9. **How do you handle a Many-to-Many relationship with additional time-based history (e.g., which employees worked on which projects, across different date ranges)?**
*Answer:* The bridge table gets extra columns like StartDate and EndDate, and the composite key often needs to include the date range or a surrogate key, since the same Employee-Project pair might repeat across different periods. *Why asked:* Tests handling of real, messy production scenarios.
10. **How would you decide between normalizing further vs keeping a wider table, when designing a new schema today?**
*Answer:* Consider: read vs write ratio (write-heavy favors normalization for consistency; read-heavy favors denormalization for speed), data volume, how often the "duplicated" data actually changes, and whether the system is OLTP or OLAP. There's no universal right answer — it's a deliberate trade-off based on actual usage patterns. *Why asked:* Open-ended senior design judgment question, no single "textbook" answer expected.

# SECTION 14: Scenario Based Questions

1. **"Your company's Customer table has columns Phone1, Phone2, Phone3 for multiple phone numbers, and adding a 4th number requires changing the table structure. What's wrong and how do you fix it?"**
*Ideal solution:* This violates 1NF (repeating groups in columns). Fix: create a separate `CustomerPhoneNumbers` table with a one-to-many relationship to Customer, allowing unlimited phone numbers without altering the table structure.
2. **"A report shows different 'Total Revenue' numbers depending on which team pulls it, even though they're querying the same underlying transactional tables."**
*Ideal solution:* Likely inconsistent JOIN logic or a poorly modelled Fact table grain; the fix is to build a single, well-defined denormalized reporting model (Star Schema) that all teams query from, rather than each team writing their own JOIN logic on raw OLTP tables.
3. **"You need to track that a Customer's shipping address at the time of an order may differ from their current address."**
*Ideal solution:* Store a snapshot of the shipping address directly on the Order table (or a related OrderAddress table) rather than only referencing the live Customer address — this preserves historical accuracy (a Slowly Changing Dimension concept).
4. **"Your database is growing slow because every report needs to JOIN 8 normalized tables just to show a simple sales summary."**
*Ideal solution:* This is a candidate for denormalization — build a separate reporting layer (Star Schema/Data Warehouse) optimized for reads, fed by ETL/ELT from the normalized OLTP system.
5. **"You're asked to model a system where a Student can enroll in multiple Courses, and a Course can have multiple Students, with an enrollment date."**
*Ideal solution:* Create a bridge table `Enrollments(StudentID FK, CourseID FK, EnrollmentDate)` with a composite key on StudentID+CourseID (or a surrogate key if repeat enrollments across terms are possible).
6. **"An employee in your model doesn't currently have a manager (e.g., the CEO). How do you represent this in a self-referencing hierarchy table?"**
*Ideal solution:* Allow the `ManagerID` Foreign Key column to be NULL for that one row, representing "no manager" — and use a LEFT JOIN when querying so the CEO still appears in reports.
7. **"You need to track price history for products because prices change monthly, but you also want fast, simple current-price lookups."**
*Ideal solution:* Keep a `Product` table with the current price, and add a separate `ProductPriceHistory` table logging every price change with effective dates — satisfying both needs without duplicating logic.
8. **"Two departments define 'Active Customer' differently, causing mismatched dashboards."**
*Ideal solution:* This isn't purely a modelling problem — it needs a single, agreed business definition encoded once into the data model/reporting layer (e.g., a `IsActive` flag or view) so everyone references the same logic instead of re-deriving it independently.
9. **"You're designing a ride-booking app model and need to know if 'Trip' should be its own entity or just columns inside 'Booking'."**
*Ideal solution:* If a Trip has its own lifecycle/attributes (start time, end time, route, driver) independent of the Booking process, model it as a separate entity related to Booking (One Booking → One Trip, or possibly One-to-Many if rebooking occurs) rather than cramming everything into one table.
10. **"Your Fact table for 'Sales' sometimes represents one row per Order and sometimes one row per Order Line Item, causing inconsistent totals."**
*Ideal solution:* This is a grain violation — the team must firmly decide and document a single grain (e.g., "one row per order line item") and rebuild the Fact table consistently at that grain.

# SECTION 15: Common Mistakes

|Mistake|Why it's a problem|Fix|
|-|-|-|
|Storing multiple values in one column (e.g., "Cardiology, Neurology")|Violates 1NF, makes searching/filtering hard|Split into a separate related table|
|No Primary Key on a table|Rows can't be uniquely identified, duplicates sneak in|Always define a Primary Key, even if surrogate|
|Overusing text columns for relationships instead of Foreign Keys|Leads to typos, inconsistent values, no referential integrity|Use Foreign Keys pointing to a proper lookup table|
|Confusing Many-to-Many with One-to-Many|Leads to data loss or incorrect duplication|Always ask "can BOTH sides repeat?" before deciding|
|Over-normalizing a reporting/analytics system|Causes painfully slow reports with too many JOINs|Denormalize deliberately for OLAP/reporting layers|
|Ignoring Fact table grain|Causes double-counting or inconsistent totals|Explicitly define and document the grain before building|
|Using Natural Keys as Primary Keys|Natural keys can change or turn out not to be unique|Prefer Surrogate Keys for stability|

# SECTION 16: Best Practices

* **Always start with a Conceptual Model** before jumping into table creation — align with business stakeholders first.
* **Use Surrogate Keys** (auto-incrementing IDs) as Primary Keys in most operational systems for stability.
* **Enforce Foreign Keys** wherever a relationship exists — don't rely on "trusting" the application layer alone.
* **Normalize OLTP systems** (transactional, write-heavy) to at least 3NF to avoid data anomalies.
* **Denormalize OLAP systems** (reporting, read-heavy) deliberately, using Star/Snowflake schemas.
* **Document the grain** of every Fact table clearly before anyone builds reports on top of it.
* **Review the model against real business questions** — if answering a common question requires 10 JOINs, reconsider the design.
* **Keep historical accuracy in mind** — snapshot data (like price or address at time of transaction) instead of only relying on "current" values.

**Why companies follow these:** A well-modelled database saves months of costly rework later, prevents inconsistent reporting across teams, and keeps performance predictable as data volume grows.

# SECTION 17: Performance Tips

|Technique|When to Use|
|-|-|
|**Index Foreign Key columns**|Always — since they're used constantly in JOINs|
|**Denormalize for reporting**|When read speed matters more than storage/duplication concerns (OLAP)|
|**Keep OLTP normalized**|When data consistency and fast, safe writes matter more (day-to-day transactions)|
|**Use surrogate integer keys, not long text keys, for joins**|Integer comparisons are much faster than string comparisons|
|**Partition large Fact tables**|When historical data grows into hundreds of millions of rows (e.g., partition by date)|
|**Pre-aggregate common metrics**|When the same summary (e.g., "Monthly Sales") is queried repeatedly — store it instead of recalculating every time|

# SECTION 18: Comparison Table

|Concept A|Concept B|Key Difference|
|-|-|-|
|**Normalization**|**Denormalization**|Normalization reduces duplication (favors writes/consistency); Denormalization adds controlled duplication (favors fast reads)|
|**OLTP**|**OLAP**|OLTP = day-to-day transactions, normalized; OLAP = analytics/reporting, often denormalized|
|**Star Schema**|**Snowflake Schema**|Star keeps dimensions flat (fewer JOINs); Snowflake further normalizes dimensions (more JOINs, less storage)|
|**Primary Key**|**Foreign Key**|PK uniquely identifies rows in its own table; FK references a PK in another table to form a relationship|
|**Surrogate Key**|**Natural Key**|Surrogate = artificial, system-generated; Natural = real-world business value (email, Aadhar)|
|**Logical Model**|**Physical Model**|Logical = technology-independent design; Physical = actual database-specific implementation|
|**One-to-Many**|**Many-to-Many**|One-to-Many needs just an FK; Many-to-Many needs a bridge/junction table|

# SECTION 19: Cheat Sheet 

```
DATA MODELLING = Blueprint for how data is structured & related

Levels:
Conceptual -> Logical -> Physical

Core building blocks:
Entity      -> becomes a Table
Attribute   -> becomes a Column
Primary Key -> uniquely identifies a row
Foreign Key -> links to another table's Primary Key

Relationships:
1:1  -> rare, used to split sensitive/optional data
1:M  -> most common (Customer -> Orders)
M:M  -> needs a Bridge/Junction table (Orders <-> Products via OrderItems)

Normalization (OLTP, reduce duplication):
1NF -> atomic values, no repeating groups
2NF -> 1NF + no partial dependency on composite key
3NF -> 2NF + no transitive dependency

Denormalization (OLAP, faster reads):
Star Schema     -> Fact table + flat Dimension tables
Snowflake Schema -> Fact table + normalized (split) Dimension tables

Golden Rule:
Normalize for WRITE-heavy systems (OLTP)
Denormalize for READ-heavy systems (OLAP)
```

* **1NF, 2NF, 3NF = "Atomic → Whole Key → Nothing but the Key"** — a classic memory phrase: 1NF wants atomic values, 2NF wants dependency on the WHOLE key, 3NF wants "nothing but the key" (no dependency on other non-key columns).

* **"OLTP = Operations, OLAP = Analysis"** — O**LT**P sounds like "little transactions" (many small quick ones); OLAP = "Look At Patterns."
* **"Star Schema looks like a star — Fact in the middle, Dimensions around it, flat and simple."**

# SECTION 24: Summary 

Data Modelling is the blueprint-design phase of building any database — deciding what Entities (tables) you need, what Attributes (columns) they hold, and how they Relate to each other, BEFORE writing a single `CREATE TABLE` statement. It progresses through three stages: **Conceptual** (business-level boxes), **Logical** (adds keys/attributes), and **Physical** (real database-specific implementation).

The core building blocks are **Primary Keys** (uniquely identify rows) and **Foreign Keys** (create relationships), with relationships classified as **One-to-One**, **One-to-Many**, or **Many-to-Many** (the last one always needing a bridge/junction table). **Normalization** (1NF, 2NF, 3NF) removes data duplication and is the standard for **OLTP** (transactional) systems, while **Denormalization** — via **Star** or **Snowflake Schemas** — intentionally trades some duplication for much faster reads, standard in **OLAP** (analytical/reporting) systems.

The most common real-world mistakes are cramming multiple values into one column (violating 1NF), skipping Foreign Key constraints, confusing One-to-Many with Many-to-Many, and building Fact tables without a clearly defined and consistent grain. A well-modelled database saves enormous rework later, keeps reporting numbers consistent across teams, and scales gracefully as a business grows — making Data Modelling arguably the single highest-leverage skill for anyone entering Data Engineering.
