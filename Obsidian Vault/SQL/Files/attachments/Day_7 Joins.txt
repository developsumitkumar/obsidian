-->> What exactly is a JOIN?
====================================================================================================================================
1) A way to fetch data together from multiple tables without duplicating data storage.
2) Works using a relationship column (usually Primary Key in one table and Foreign Key in another).
3) The database matches rows where the join condition is true.
====================================================================================================================================
-->> Uses of JOIN in SQL
====================================================================================================================================
Purpose	                | Example
====================================================================================================================================
Fetch related data	    | Get customer details along with their orders.
Avoid data duplication	| Store customer info in one table, orders in another, then combine them when needed.
Data analysis	        | Compare or aggregate data across multiple tables.
Reporting	            | Generate combined reports from different datasets.
Data validation	        | Check if related records exist in another table.
====================================================================================================================================
-->> Primary Key vs Foreign Key
Feature	      | Primary Key	Foreign Key
Definition	  | A column (or set of columns) that uniquely identifies each row in a table.	| A column in one table that refers to the Primary Key in another table.
Purpose	      | Ensure each record is unique in the table.	| Create a relationship between two tables.
Uniqueness	  | Must be unique for every row.	| Can have duplicates (multiple rows can refer to the same primary key).
NULL Allowed? | No — cannot have NULL values.	| Yes — foreign key can be NULL if the relationship is optional.
Example	      | student_id in students table.	| department_id in students table referring to department_id in departments table.
====================================================================================================================================
Other Common Keys in SQL
Key Type	    | Description	Example
Candidate Key	| All possible columns that could uniquely identify rows. One of these becomes the Primary Key.	| student_id or email in students table.
Composite Key	| Primary key made of multiple columns.	| (course_id, student_id) in enrollments table.
Alternate Key	| Candidate key that is not chosen as the primary key.	| If email is unique but student_id is primary, then email is alternate key.
Super Key	    | Any set of columns that uniquely identify rows (includes candidate keys + extra columns).	| (student_id, name) — still unique but has extra column.
Unique Key	    | Ensures column values are unique, but allows one NULL (depends on DBMS).	| email in students table.
=====================================================================================================================================
-->>Quick Analogy for Students:

Primary Key = Your Aadhaar number (unique to you, can’t be empty).

Foreign Key = Your school’s record of which Aadhaar number belongs to which student.

Unique Key = Your email — also unique, but you could choose not to give it (NULL).

Composite Key = Your exam roll number + subject code combined to make a unique record.
===================================================================================================================================
Join Type	| Layman Analogy	                                                                | What It Shows
INNER JOIN	| Only friends who are on both your phone contacts and Facebook.	                | Rows that match in both tables.
LEFT JOIN	| All your phone contacts, and if they have Facebook, show their profile;           | if not, leave blank.	All rows from left table + matched rows from right.
RIGHT JOIN	| All your Facebook friends, and if they’re also in your phone contacts, show that; | else blank.	All rows from right table + matched from left.
FULL JOIN	| All people from phone contacts + all Facebook friends (no one is left out).	    | All rows from both tables, matching where possible.
CROSS JOIN	| Every phone contact matched with every Facebook friend.	                        | Cartesian product (all combinations).
SELF JOIN	| You check people in the same list who belong to the same group.	                | Table joined with itself.
===================================================================================================================================
-- Step 1: INNER JOIN
SELECT s.name, s.department_id, sub.subject_name
FROM students s
INNER JOIN subjects sub
ON s.department_id = sub.department_id;

-- Step 2: LEFT JOIN
SELECT s.name, s.department_id, sub.subject_name
FROM students s
LEFT JOIN subjects sub
ON s.department_id = sub.department_id;

-- Step 3: RIGHT JOIN
SELECT s.name, s.department_id, sub.subject_name
FROM students s
RIGHT JOIN subjects sub
ON s.department_id = sub.department_id;

-- Step 4: FULL OUTER JOIN (MySQL workaround using UNION)
SELECT s.name, s.department_id, sub.subject_name
FROM students s
LEFT JOIN subjects sub ON s.department_id = sub.department_id
UNION
SELECT s.name, s.department_id, sub.subject_name
FROM students s
RIGHT JOIN subjects sub ON s.department_id = sub.department_id;

-- Step 5: CROSS JOIN
SELECT s.name, sub.subject_name
FROM students s
CROSS JOIN subjects sub;

-- Step 6: SELF JOIN (Example: students in same department)
SELECT A.name AS Student1, B.name AS Student2, A.department_id
FROM students A
JOIN students B
ON A.department_id = B.department_id
AND A.student_id < B.student_id;

-->> Rules Before Joining Two Tables
1. Understand the Relationship
Rule: Know the primary key–foreign key relationship.

Why: Joins work best when there is a logical link (e.g., students.department_id ↔ subjects.department_id).

Avoid: Joining on columns that have no logical connection — it produces meaningless results or huge cartesian outputs.

2. Match Data Types
Rule: The columns you join on must have compatible data types (e.g., both INT or both VARCHAR).

Why: Mismatched types cause implicit conversions → slow queries & possible mismatches.

Avoid: Joining INT to VARCHAR or DATE to TEXT without conversion.

3. Avoid Ambiguity
Rule: Always prefix columns with table aliases (s.name, sub.subject_name).

Why: If both tables have a column with the same name (e.g., department_id), SQL will throw an error or pick the wrong one.

Avoid: Using unqualified column names in joins.

4. Choose the Correct Join Type
Rule: Decide whether you want only matches (INNER), all left table (LEFT), all right table (RIGHT), or everything (FULL).

Why: Picking the wrong join type changes the meaning of your query.

Avoid: Using INNER JOIN when you actually want to keep unmatched records.

5. Minimize Data Early
Rule: Use WHERE clauses to filter before or immediately after joining.

Why: This reduces memory usage and speeds up joins.

Avoid: Joining huge tables without filtering.

6. Beware of Duplicates
Rule: Check if the join column is unique on at least one side.

Why: If both sides have duplicates, you might get unexpected many-to-many results.

Avoid: Blindly joining without checking uniqueness — it can explode row counts.

7. Use Meaningful Join Conditions
Rule: Always use ON for join conditions, not WHERE for INNER joins (in old SQL syntax).

Why: Mixing join logic into WHERE can cause confusion in LEFT/RIGHT joins — especially when filtering NULLs.

Avoid: FROM A, B WHERE A.id = B.id style (old implicit join).

8. Handle NULL Values
Rule: Expect NULLs when using LEFT/RIGHT/FULL joins.

Why: Missing matches will have NULL in columns from the other table.

Avoid: Assuming all columns will have values after an outer join.

9. Keep Joins Readable
Rule: Use short, meaningful aliases (s for students, sub for subjects).

Why: Makes complex queries easier to read & debug.

Avoid: Joining more than 3–4 tables in one go without formatting.

10. Test with Small Data
Rule: First run the join on a few rows to confirm logic.

Why: Prevents surprises in large datasets.

Avoid: Running untested joins on millions of rows.
