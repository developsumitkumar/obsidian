# Incremental Gold Aggregation with Delta `MERGE`

> [!summary] Core Idea  
> For small datasets, it is perfectly reasonable to **read all Silver history, recompute Gold from scratch, and overwrite Gold**.
> 
> As the dataset grows, this becomes expensive. Instead, identify **which part of Silver changed**, recompute only that affected slice, and **MERGE** those results into the existing Gold Delta table.

---

## 1. The Starting Point

Assume the **Silver layer** contains cleaned transaction-level data.

```text
Silver
------------------------------------------------
id   created_at   category       amount
1    2026-01-05   Food             500
2    2026-01-10   Travel          1000
3    2026-02-03   Food             700
4    2026-02-15   Shopping        2000
5    2026-03-01   Food             300
```

Gold contains aggregated business data:

```text
Gold
--------------------------------
month      category       total
2026-01    Food             500
2026-01    Travel          1000
2026-02    Food             700
2026-02    Shopping        2000
2026-03    Food             300
```

The transformation is essentially:

```text
Silver Transaction Data
          ↓
GROUP BY month, category
          ↓
SUM(amount)
          ↓
Gold Monthly Summary
```

---

# 2. Approach 1 — Full Gold Recompute

A simple first implementation might be:

```python
silver_full = spark.read.parquet(str(silver_path))

gold_df = build_monthly_spending(silver_full)

write_parquet(
    gold_df,
    gold_path,
    mode="overwrite"
)
```

This means:

```text
Read ALL Silver History
          ↓
Recalculate ALL Aggregates
          ↓
Create New Gold Dataset
          ↓
Overwrite Existing Gold
```

### Example

Suppose Silver contains data from:

```text
January
February
March
April
...
September
```

Even if today's pipeline only adds one September transaction, the pipeline still reads:

```text
January → September
```

and recalculates everything.

---

## 3. Why Full Recompute Is Actually Good Initially

Full recomputation is:

- Simple
    
- Easy to understand
    
- Easy to debug
    
- Idempotent when designed correctly
    
- Less likely to leave stale aggregates
    
- Safe with historical corrections
    

For example, suppose an old February transaction changes:

```text
OLD
2026-02-03 | Food | ₹700

NEW
2026-02-03 | Food | ₹900
```

Because the next run reads **all Silver history**, February is automatically recalculated.

You don't need special logic to determine that February changed.

> [!important]  
> **Full recomputation is not bad engineering.**
> 
> For small datasets, it is often the safest and simplest solution.

---

# 4. The Scaling Problem

Suppose Silver eventually contains:

```text
2023 → 100 million rows
2024 → 120 million rows
2025 → 150 million rows
2026 → 180 million rows
```

Total:

```text
550 million rows
```

Tonight only:

```text
50,000 new/changed rows
```

arrive.

A full recompute still does:

```text
Read 550,000,000 rows
          ↓
Aggregate everything
          ↓
Rebuild every month
          ↓
Overwrite Gold
```

Even though perhaps only:

```text
September 2026
```

changed.

This wastes:

- Compute
    
- I/O
    
- Processing time
    
- Money
    

---

# 5. Better Approach — Incremental Gold

Instead of asking:

> "Recalculate the entire Gold table."

ask:

> **"Which parts of Gold could have changed because of this run?"**

Suppose today's Silver increment contains:

```text
created_at    category    amount
--------------------------------
2026-09-18    Food          500
2026-09-19    Travel       1200
2026-09-20    Food          700
```

All changed records belong to:

```text
2026-09
```

Therefore only **September 2026** needs to be recomputed.

```text
Jan   Feb   Mar   Apr ... Aug   SEP
 ×     ×     ×     ×      ×     ✓
                              Recompute
```

---

# 6. Step 1 — Find the Affected Months

```python
affected_months = (
    silver_increment_df
    .select(
        date_format("created_at", "yyyy-MM")
        .alias("month")
    )
    .distinct()
)
```

Example input:

```text
2026-09-18
2026-09-19
2026-09-20
2026-08-15
```

After extracting month:

```text
2026-09
2026-09
2026-09
2026-08
```

After `.distinct()`:

```text
affected_months
---------------
2026-08
2026-09
```

Now the pipeline knows:

> August and September may have changed.

---

# 7. Don't Simply Add New Amounts to Gold

A tempting solution is:

```text
Current September Food = ₹10,000

New Food transaction = ₹500

New Gold = ₹10,500
```

This works for pure inserts.

But what if the incoming record is a **correction**?

Suppose an existing transaction changes:

```text
OLD
Food = ₹1000

NEW
Food = ₹700
```

Simply adding ₹700 would be wrong because ₹1000 is already included in Gold.

Correct calculation requires:

```text
₹10,000 - ₹1,000 + ₹700
```

Things become even more complicated with:

```text
Updates
Deletes
Duplicates
Late-arriving records
Backdated corrections
Category changes
```

> [!important] Professional Pattern  
> **Don't increment the aggregate blindly.**
> 
> Instead:
> 
> 1. Identify the affected slice.
>     
> 2. Read the underlying Silver rows for that slice.
>     
> 3. Recompute the aggregate correctly.
>     
> 4. MERGE the result into Gold.
>     

---

# 8. Recompute Only the Affected Slice

Suppose only September changed.

Instead of:

```text
ALL SILVER
    ↓
Aggregate everything
```

do:

```text
Silver
│
├── January      ❌
├── February     ❌
├── March        ❌
├── ...
├── August       ❌
│
└── September    ✅
        ↓
Recalculate September
        ↓
partial_gold_df
```

Suppose September Silver contains:

```text
Food       500
Food       700
Food       300
Travel    1000
Travel     500
```

Recalculation produces:

```text
month      category    total
----------------------------
2026-09    Food         1500
2026-09    Travel       1500
```

This becomes:

```text
partial_gold_df
```

---

# 9. Now Use Delta `MERGE`

Existing Gold:

```text
month      category    total
----------------------------
2026-07    Food         9000
2026-08    Food        11000
2026-09    Food        12000
2026-09    Travel       8000
```

Recalculated Gold slice:

```text
partial_gold_df

2026-09    Food        13500
2026-09    Travel       9000
2026-09    Shopping     4000
```

We want:

```text
July        → untouched
August      → untouched
September   → updated
```

Use:

```python
gold_table = DeltaTable.forPath(
    spark,
    "output/gold/monthly_spending"
)

(
    gold_table.alias("target")
    .merge(
        partial_gold_df.alias("source"),
        """
        target.month = source.month
        AND target.category = source.category
        """
    )
    .whenMatchedUpdateAll()
    .whenNotMatchedInsertAll()
    .execute()
)
```

---

# 10. How `MERGE` Works

Think:

```text
TARGET = Existing Gold

SOURCE = Recalculated affected rows
```

Delta compares:

```text
target.month = source.month

AND

target.category = source.category
```

### Match exists

```text
TARGET
2026-09 | Food | 12000

SOURCE
2026-09 | Food | 13500
```

Because the key matches:

```text
WHEN MATCHED
      ↓
UPDATE
```

Result:

```text
2026-09 | Food | 13500
```

### Match doesn't exist

Suppose:

```text
SOURCE
2026-09 | Shopping | 4000
```

There is no Shopping row for September in Gold.

Therefore:

```text
WHEN NOT MATCHED
       ↓
INSERT
```

Final Gold:

```text
2026-07 | Food       |  9000   ← untouched
2026-08 | Food       | 11000   ← untouched
2026-09 | Food       | 13500   ← updated
2026-09 | Travel     |  9000   ← updated
2026-09 | Shopping   |  4000   ← inserted
```

---

# 11. Why Delta Lake Helps

Delta Lake provides transactional operations such as:

```text
INSERT
UPDATE
DELETE
MERGE
```

The Gold update becomes a transaction:

```text
Gold Version 10
       ↓
     MERGE
       ↓
Update Food
Update Travel
Insert Shopping
       ↓
    COMMIT
       ↓
Gold Version 11
```

Readers see a valid committed table state rather than an arbitrary halfway update.

# 12. The Important Edge Case — Backdated Corrections

Suppose today is:

```text
September 2026
```

but someone corrects a transaction from:

```text
January 2026
```

Example:

```text
OLD

2026-01-10
Food
₹500
```

becomes:

```text
NEW

2026-01-10
Food
₹900
```

January is now an affected month.

Your pipeline must detect:

```text
affected_months
---------------
2026-01
```

and recompute January.

If your pipeline assumes:

```text
affected_month = current_month
```

it will only recompute September.

January Gold will silently remain incorrect.

> [!warning] Incremental Processing Risk  
> Once you stop recomputing everything, **correctly identifying what changed becomes part of your correctness logic.**
> 
> Late-arriving records and backdated corrections must be included when determining affected partitions.

# 13. Full Recompute vs Incremental + MERGE

|Full Recompute|Incremental + MERGE|
|---|---|
|Reads all Silver|Reads affected Silver slices|
|Recalculates all Gold|Recalculates affected Gold|
|Overwrites Gold|MERGEs changed rows|
|Simple|More complex|
|Easy correctness|Change detection must be correct|
|More expensive at scale|Efficient at scale|
|Good for small datasets|Good for large datasets|
|Historical corrections naturally included|Historical corrections must be detected|

# 14. Evolution of the Pipeline

## Version 1 — Small Dataset

```text
        SILVER
     All History
          │
          ↓
     GROUP BY
          │
          ↓
        GOLD
          │
          ↓
Overwrite Everything
```

### Advantage

```text
Simple + Safe + Correct
```

---

## Version 2 — Large Dataset

```text
New / Changed Silver Rows
           │
           ↓
 Find Affected Months
           │
           ↓
   Example: September
           │
           ↓
Read September Silver Rows
           │
           ↓
Recalculate September
           │
           ↓
    partial_gold_df
           │
           ↓
        MERGE
           │
           ↓
Existing Gold Delta Table
           │
           ↓
Only affected rows change
```

---

> [!tip] Key Concept  
> **Incremental aggregation does NOT necessarily mean adding today's amount to yesterday's aggregate.**
> 
> A safer pattern is:
> 
> **Detect affected slice → Recompute that slice from Silver → MERGE into Gold**

# Interview Answer

### Q: How would you make Gold aggregation incremental?

> For a small dataset, I would initially use a full recompute because it is simple and provides strong correctness — read the complete Silver table, regenerate the Gold aggregates, and overwrite Gold.
> 
> As the dataset scales, I would identify the partitions or business keys affected by each incremental Silver load. I would then recompute the aggregates only for those affected slices from the underlying Silver data and MERGE the results into the existing Delta Gold table.
> 
> I would also ensure that late-arriving records and backdated corrections are considered when determining affected partitions; otherwise, an incremental pipeline could leave stale aggregates.

```text
SMALL DATA

Silver Full
    ↓
Aggregate Everything
    ↓
Overwrite Gold

        ↓ DATA GROWS ↓

LARGE DATA

Silver Increment
    ↓
Find affected month(s)
    ↓
Read affected Silver slice
    ↓
Recompute affected aggregates
    ↓
MERGE into Gold
    ↓
UPDATE existing rows

```

## One-Line Memory Trick

> **Full recompute = rebuild the whole house. Incremental MERGE = identify the damaged rooms, rebuild those rooms correctly, and replace only those parts.**
