`DELETE` removes records from the **logical table**.

Suppose:

```
id    category     amount
-------------------------
101   Food          500
102   Travel        1000
103   Shopping      1200
```

Transaction `103` was created accidentally.

```
DELETE FROM silver_transactions
WHERE id = 103;
```

Logical result:

```
101   Food      500
102   Travel   1000
```

But here's where your Delta knowledge becomes useful.

Deleting a row does **not necessarily mean the corresponding old Parquet file immediately disappears from storage**.

Conceptually:

```sql
Before

part-A.parquet
contains:
101
102
103

       ↓ DELETE 103

Delta may create:

part-B.parquet
containing:
101
102

       ↓

_delta_log

REMOVE part-A
ADD part-B
```

The old file can remain physically present temporarily.

Why?

Because Delta may need it for:

```
Time Travel
Previous table versions
Recovery
```

This connects directly to `VACUUM`, which we'll discuss shortly.

### Pipeline impact

Deletes are another reason incremental Gold processing isn't simply:

```
old_total + new_amount
```

Imagine:

```
Gold September Food = ₹10,000
```

Then a bad ₹500 transaction is deleted from Silver.

Correct Gold should become:

```
₹9,500
```

That's why our pattern was:

```
Detect September changed
        ↓
Read September from Silver again
        ↓
Recalculate
        ↓
MERGE corrected aggregate into Gold
```

### Remember

```
INSERT → New row
UPDATE → Existing row changes
DELETE → Existing row removed
```
