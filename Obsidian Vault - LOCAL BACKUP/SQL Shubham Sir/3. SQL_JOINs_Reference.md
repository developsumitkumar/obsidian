# SQL JOINs — Complete Reference

## What exactly is a JOIN?

> [!quote] Definition
> 1. A way to fetch data together from multiple tables without duplicating data storage.
> 2. Works using a relationship column (usually a Primary Key in one table and a Foreign Key in another).
> 3. The database matches rows where the join condition is true.

## Uses of JOIN

| Purpose | Example |
|---|---|
| Fetch related data | Get customer details along with their orders |
| Avoid data duplication | Store customer info in one table, orders in another, combine when needed |
| Data analysis | Compare or aggregate data across multiple tables |
| Reporting | Generate combined reports from different datasets |
| Data validation | Check if related records exist in another table |

## Primary Key vs Foreign Key

| Feature | Primary Key | Foreign Key |
|---|---|---|
| Definition | Uniquely identifies each row in a table | Refers to the Primary Key in another table |
| Purpose | Ensure each record is unique in the table | Create a relationship between two tables |
| Uniqueness | Must be unique for every row | Can have duplicates |
| NULL allowed? | No | Yes, if the relationship is optional |
| Example | `student_id` in `students` | `department_id` in `students`, referring to `departments.department_id` |

### Other common keys

| Key type | Description | Example |
|---|---|---|
| Candidate Key | All possible columns that could uniquely identify rows; one becomes the PK | `student_id` or `email` in `students` |
| Composite Key | Primary key made of multiple columns | `(course_id, student_id)` in `enrollments` |
| Alternate Key | A candidate key not chosen as the primary key | `email`, if `student_id` is the PK |
| Super Key | Any column set that uniquely identifies rows (candidate keys + extras) | `(student_id, name)` |
| Unique Key | Ensures uniqueness, but allows one NULL (DBMS-dependent) | `email` in `students` |

> [!example] Quick analogy
> - **Primary Key** = your Aadhaar number (unique, can't be empty)
> - **Foreign Key** = your school's record of which Aadhaar number belongs to which student
> - **Unique Key** = your email — also unique, but optional (NULL allowed)
> - **Composite Key** = exam roll number + subject code combined, unique only together

## Join Types — layman analogies

| Join type | Analogy | What it shows |
|---|---|---|
| INNER JOIN | Only friends who are on both your phone contacts and Facebook | Rows that match in both tables |
| LEFT JOIN | All your phone contacts; show Facebook profile if they have one, else blank | All rows from left + matched rows from right |
| RIGHT JOIN | All your Facebook friends; show phone contact info if matched, else blank | All rows from right + matched from left |
| FULL JOIN | All people from phone contacts + all Facebook friends, no one left out | All rows from both, matched where possible |
| CROSS JOIN | Every phone contact matched with every Facebook friend | Cartesian product — every combination |
| SELF JOIN | Checking people in the same list who belong to the same group | Table joined with itself |

## Syntax reference

```sql
-- INNER JOIN
SELECT s.name, s.department_id, sub.subject_name
FROM students s
INNER JOIN subjects sub
ON s.department_id = sub.department_id;

-- LEFT JOIN
SELECT s.name, s.department_id, sub.subject_name
FROM students s
LEFT JOIN subjects sub
ON s.department_id = sub.department_id;

-- RIGHT JOIN
SELECT s.name, s.department_id, sub.subject_name
FROM students s
RIGHT JOIN subjects sub
ON s.department_id = sub.department_id;

-- FULL OUTER JOIN (MySQL workaround using UNION, since MySQL has no native FULL JOIN)
SELECT s.name, s.department_id, sub.subject_name
FROM students s
LEFT JOIN subjects sub ON s.department_id = sub.department_id
UNION
SELECT s.name, s.department_id, sub.subject_name
FROM students s
RIGHT JOIN subjects sub ON s.department_id = sub.department_id;

-- CROSS JOIN
SELECT s.name, sub.subject_name
FROM students s
CROSS JOIN subjects sub;

-- SELF JOIN (students in the same department)
SELECT A.name AS Student1, B.name AS Student2, A.department_id
FROM students A
JOIN students B
ON A.department_id = B.department_id
AND A.student_id < B.student_id;
```

> [!tip] Why `A.student_id < B.student_id` in the SELF JOIN
> Prevents matching a student with themselves and prevents duplicate reversed pairs (Student1=A/Student2=B *and* Student1=B/Student2=A both appearing).

## Rules before joining two tables

1. **Understand the relationship** — know the PK–FK link (`students.department_id ↔ subjects.department_id`). Joining on unrelated columns produces meaningless or huge cartesian results.
2. **Match data types** — join columns must be compatible (`INT` to `INT`, not `INT` to `VARCHAR`). Mismatches cause implicit conversions, slow queries, and possible mismatches.
3. **Avoid ambiguity** — always prefix columns with table aliases (`s.name`, `sub.subject_name`). Unqualified names on shared column names cause errors or wrong picks.
4. **Choose the correct join type** — INNER (only matches), LEFT (all left + matches), RIGHT (all right + matches), FULL (everything). Wrong choice changes the query's entire meaning.
5. **Minimize data early** — filter with `WHERE` before or immediately after joining, to reduce memory usage and speed things up.
6. **Beware of duplicates** — check the join column is unique on at least one side; duplicates on both sides can explode row counts unexpectedly (many-to-many blowup).
7. **Use `ON` for join conditions**, not `WHERE` — mixing join logic into `WHERE` causes confusion in LEFT/RIGHT joins, especially with NULL filtering.
8. **Handle NULLs** — expect NULLs in outer-joined columns wherever no match was found; never assume every column will be populated after an outer join.
9. **Keep joins readable** — use short, meaningful aliases (`s`, `sub`); avoid joining more than 3–4 tables without careful formatting.
10. **Test with small data first** — confirm logic on a few rows before running on millions.
